# Historique des changements

## 30 octobre 2026 — SDK Billing 1.2.0

Clients sans téléphone, références externes, quatre fréquences, essais et périodes,
lecture canonique, import et factures dans les trois SDK. Charges utiles webhook
typées et pagination préservée. [Guide Billing français/anglais](/guides/subscriptions),
avec ACTIVE ≠ paid, cycle webhook et parcours TEST. Python/PHP restent installables
par source ; publication de registre conditionnée aux accès disponibles.


## Octobre 2026

### Inscription ouverte, sans abonnement (17 octobre)

- L'inscription est ouverte à tous, sans invitation. Le compte démarre dans la sandbox gratuite.
- Plus d'abonnement SahelPay : le passage en live dépend uniquement du KYC approuvé et de l'accès production. SahelPay facture une commission de service par transaction réussie.
- Les paiements portent désormais `settlement_mode` (`platform` : fonds encaissés via SahelPay ; `direct` : fonds arrivés sur votre propre compte marchand), y compris dans les webhooks (`funds_held_by_sahelpay`, `commission_collection`). Un paiement `direct` n'est pas remboursable via SahelPay.

### SDKs 1.1.0 (17 octobre)

- **Corrigé** : `payments.create()` envoie `description` au niveau racine. Les versions 1.0.0 JavaScript et Python la plaçaient dans `metadata`, où l'API l'écrasait : la description n'apparaissait ni dans le dashboard ni dans les webhooks.
- **Corrigé** : `paymentLinks.create()` avec un montant (`price` ou `fixed_amount`) crée un lien à prix fixe (`amount_mode: FIXED`). En 1.0.0 les trois SDKs créaient un lien à montant libre (`OPEN`) : vérifiez les liens créés par SDK.
- **Corrigé** (Python) : `payments.search()` et `payments.recommend()` encodent leurs paramètres (le `+` d'un numéro était lu comme un espace). `PaymentLink` accepte un lien à montant libre (`price: null`).
- **Changé** : la vérification de signature n'accepte plus qu'`X-SahelPay-Signature: t=...,v1=...`. L'ancien repli (HMAC du corps seul, sans horodatage) est retiré : SahelPay ne l'émet pas et il n'offrait aucune protection contre le rejeu.
- **Changé** : `customer_phone` est facultatif avec le checkout hébergé (la page le demande au payeur). `callback_url` est ignoré (avertissement en Python) : les webhooks partent vers les endpoints de l'application.
- **Ajouté** : `payments.expire()`, `paymentLinks.update()` / `delete()` / `retrieveById()`, livraisons webhook (`listLogs`, `retrieveLog`, `retry`, `stats`, `listEvents`, `retrieveEvent`), paiement sécurisé (`secureOrders.*`), types `refund.pending` et `payment.cancelled`, `id` sur l'événement webhook Python.
- Le SDK JavaScript `@sahelpay/sdk` 1.1.0 est publié sur npm. PHP et Python : installation depuis le dépôt en attendant Packagist et PyPI.

### Isolation test / live et webhooks fiables

- Une clé ne lit que les objets de son mode : une clé `sk_test_...` ne voit pas les paiements live, et inversement. Même règle pour les remboursements, liens, abonnements et le portail client.
- Endpoints webhook par application, avec un mode (`test`, `live` ou les deux) : un événement de test ne part plus vers un endpoint live.
- Les webhooks de paiement sont écrits dans la même transaction que le changement de statut, puis relayés : aucun événement perdu. Un même événement garde le même `id` d'une relance à l'autre : dédupliquez dessus.
- `refund.pending` est émis à chaque demande de remboursement.
- `client_reference` est renvoyé par `GET /v1/payments/{id}/status`, `/details` et `/search`.
- Le checkout hébergé demande le numéro Orange Money du payeur avant le transfert s'il n'a pas été fourni. Les paiements par transfert ajoutent à `data.metadata` du webhook `amount_to_pay`, `amount_received`, `surplus` et `manual_merchant_confirmation`.

### Un seul moyen de paiement

- Le mobile money au Mali est le **seul** moyen de paiement ; les autres fournisseurs ont été retirés.
- Toute autre valeur de `provider` / `payment_method` est rejetée avec `400`, jamais routée ailleurs.
- `GET /v1/payments/providers` et `GET /v1/payments/recommend` ne renvoient plus que le moyen de paiement disponible.

### Production sur demande, sandbox gratuite

- La sandbox est gratuite et ouverte à tous les comptes.
- L'accès production est soumis à une validation et à un contrat distinct précisant son périmètre et les rôles de chaque partie (`401 PRODUCTION_KEY_DISABLED` ou `403 PAID_SUBSCRIPTION_REQUIRED` sinon). Voir [Passer en production](/guides/going-live).
- L'ouverture de compte se fait sur demande à [support@sahelpay.africa](mailto:support@sahelpay.africa?subject=Demande%20d%27acc%C3%A8s%20SahelPay).

### Paiements

- `X-Idempotency-Key` est **obligatoire** sur `POST /v1/payments`. Rejouer la même clé renvoie le même paiement ; une demande différente sous la même clé renvoie `409`.
- Le checkout hébergé reprend la même session de paiement après un rechargement ou un double clic.
- Après un paiement **confirmé**, la page de paiement redirige automatiquement le client vers votre `return_url` (HTTPS, hors domaines SahelPay). Aucune redirection automatique pour un paiement en attente ou échoué.
- Option de test explicite : `metadata.sahelpay_mock` (simulateur, option SDK `mock`) est distincte de `metadata.sandbox` (sandbox de l'opérateur). Les deux sont refusées en production.
- `payment.expired` est émis à toute expiration (délai écoulé, `POST /v1/payments/{id}/expire`, réconciliation). Un paiement n'a pas de statut « annulé » : un abandon finit en `payment.expired`.

### Fonctions retirées ou restreintes

- **OPR** (`/v1/opr/*`) : limité à la sandbox.
